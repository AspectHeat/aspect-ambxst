⚠ OBSOLETE — do not implement

Superseded 2026-07-28. supergfxctl has been uninstalled from Zephyrus and is deprecated upstream — both the Arch wiki and asus-linux.org state "supergfxctl is being phased out and its use is unadvised." This widget targets a tool that no longer exists on the machine.

The problem it was meant to help with — Hybrid mode draining the battery — had nothing to do with graphics-mode switching. The dGPU was never reaching D3cold because a hand-written nvidia-dgpu-pm-on.service pinned its HDA audio function to power/control=on, and a PCI device cannot enter D3cold unless every function can runtime-suspend. One systemctl disable recovered ~3.5 W and took dGPU suspend residency from 0% to ~90%. Mode switching is no longer needed for battery life.

Kept only as a record of the design work and the research it produced. If a GPU widget is ever wanted, it should target asusctl armoury (the supported firmware-attribute interface) and derive mode from sysfs (dgpu_disable / gpu_mux_mode) rather than trusting any daemon's reported mode. Full write-up: .planning/2026-07-28-zephyrus-gpu-stack-remediation/results.md.

1. How supergfxctl actually works

Everything below was probed against the live daemon on Zephyrus (supergfxctl 5.2.7) and cross-checked against upstream source. The single most important fact: you never have to guess which session action a mode change needs — the daemon computes it and tells you.

Architecture

  • supergfxd is a system D-Bus service (org.supergfxctl.Daemon at /org/supergfxctl/Gfx), started Before=display-manager.service. It survives session teardown — which is what makes the whole logout dance work.
  • supergfxctl is a thin client. Every flag round-trips over D-Bus, so all of them fail when the daemon is down — including --version. That makes -v a perfectly good single-shot availability probe (see Bostrom, below).
  • Persistent config lives at /etc/supergfxd.conf (JSON, mode 0644 — readable without root, so a Quickshell FileView can watch it).

Parsing gotchas. -s emits a bracketed comma-space list, not JSON — strip [] and split on ", ". Error output is written with ANSI colour escapes (\x1b[0;31m…) — strip them before matching, or every error string comparison silently fails. Mode names are case-sensitive on input.

Full enum: Logout, Reboot, SwitchToIntegrated, AsusEgpuDisable, Nothing. The latter two only arise via Vfio / AsusEgpu, which this pass does not expose.

always_reboot overrides the entire matrix. Upstream controller.rs: if config.always_reboot { Reboot } else { mode_change_action(…) }. Zephyrus has always_reboot: true, so on the primary dev machine every graphics switch demands a full reboot and the Logout button would never once be the correct answer. Any design that hardcodes "Logout for Hybrid⇄Integrated, Reboot for Mux" is wrong on the machine it will be developed on. Read the flag; do not assume it.

What happens after a Logout-class change is staged

  1. -m Hybrid returns immediately with the required action. The change is now staged, not applied.
  2. With no_logind: false, supergfxd runs a WaitLogout action — it blocks on logind until the graphical session count reaches zero, bounded by logout_timeout_s (180 s on both machines).
  3. It then performs StopDisplayManager → unbind/rebind/hotplug the dGPU → StartDisplayManager.

Because step 1 returns straight away, there is no set-then-logout race — call -m, check the exit code, then trigger the session action. This resolves the open question the previous draft flagged.

4. Goal & non-goals

Goal

  • Expose live supergfxctl modes in the battery popup, under power profiles, with identical segmented chrome.
  • On selection, present the one session action the daemon requires, plus Cancel — never a menu of guesses.
  • Hide the row entirely when supergfxd is unavailable — no dead UI, no regression on machines without hybrid graphics.
  • Survive a Quickshell hot reload without losing or misreporting a staged mode change.

Non-goals (this pass)

  • No asusctl fan / Aura / battery-limit widgets — separate, Zephyrus-only work.
  • No dashboard / launcher / OSD surface for GPU mode.
  • No Vfio, AsusEgpu, NvidiaNoModeset or None. Filter them out of -s even when enumerated: they introduce the SwitchToIntegrated and AsusEgpuDisable actions, which need multi-step UI this pass does not build.
  • No editing /etc/supergfxd.conf from the shell — read-only. Toggling always_reboot is a root operation and a footgun.
  • No enabling supergfxd at boot on Bostrom; document only.

Predict, then verify

The daemon only reports the required action after -m has staged the change — so a naive "click → ask daemon → confirm" flow leaves a live staged change behind on every misclick in a bar popup. Instead:

  1. Predict client-side for the confirm strip label: always_reboot ? Reboot : matrix(target, current). The matrix is nine cells and upstream-stable; always_reboot comes from the config file.
  2. Verify on confirm: run -m, parse the returned action. If it matches the prediction, run the session command. If it differs, do not run it — re-render the strip with the daemon's answer and let the user press again.

Cancel therefore costs nothing: no D-Bus call was ever made, so there is no staged change to unwind. This is the main correction to the previous draft's flow.

6. The logout question

There are several ways to "log out" on these machines and they are not interchangeable for this feature. supergfxd is not watching for a compositor to die — it is watching logind for the graphical session count to hit zero. Anything that fails to close the logind session leaves the daemon blocked for logout_timeout_s (180 s) and the mode change silently does not happen.

What the session actually looks like

Both machines share the same chain — which is convenient, and not obvious:

sddm → sddm-helper → uwsm start -e -D Hyprland hyprland.desktop
                       ├─ uwsm/signal-handler.sh  wayland-session-envelope@hyprland.desktop.target
                       └─ systemctl --user start --wait wayland-session-envelope@…

  ...and separately, under the *user manager*:
      systemd --user → start-hyprland → Hyprland

Note that Hyprland is not inside the session scope. It runs under systemd --user; the session scope holds sddm-helper and the uwsm envelope waiters. Session teardown therefore depends on uwsm propagating compositor exit back up to sddm-helper — it is not automatic.

Linger=yes — the likely reason logout never worked here. loginctl show-user jayr -p Linger returns yes, so user@1000.service survives session teardown. Terminating the graphical session kills the systemctl --user start --wait client but does not inherently stop the envelope target — so Hyprland can outlive the session holding DRM FDs on the NVIDIA node, and supergfxd then unbinds under a live compositor. That is precisely the failure the June 12 incident note describes. uwsm's signal-handler.sh exists to stop the target on session death, so it may win the race; whether it does is unverified.

Decisive test, one command from SSH: loginctl terminate-session <id> — then check whether Hyprland is still running. Settle this before shipping a Logout button, and before anyone flips always_reboot to false.

7. Architecture

Follow the reactive singleton + Process pattern in modules/services/PowerProfile.qml: 2 s startup Timer, _initialized guard, capability probe first, Qt.callLater around follow-up process launches. All CLI parsing lives in the service; the UI binds to properties only.

SuperGfx singleton API

pragma Singleton

Singleton {
    property bool   isAvailable:   false
    property var    availableModes: []      // filtered: Integrated | Hybrid | AsusMuxDgpu
    property string currentMode:   ""
    property bool   alwaysReboot:  false    // from /etc/supergfxd.conf via FileView
    property string stagedMode:    ""       // from -P, survives hot reload
    property string stagedAction:  ""       // from -p, survives hot reload

    signal modeStaged(string mode, string action)   // action: logout|reboot|none
    signal modeSetFailed(string reason)

    function initialize()
    function refresh()                              // -g, -s, -p, -P
    function setMode(mode)                          // -m <mode>; emits modeStaged
    function predictAction(target)                  // alwaysReboot ? "reboot" : matrix(...)
    function getModeIcon(mode)
    function getModeDisplayName(mode)               // AsusMuxDgpu → "Mux dGPU"
}
Never prefix with sudo. supergfxd is a system service with a permissive D-Bus policy; the client runs as the user. Surface stderr through modeSetFailed — after stripping ANSI escapes.

Hot-reload correctness

The dev loop reloads Quickshell constantly, and a staged mode change lives in the daemon, not the shell. If the shell reloads after staging, UI-local pendingMode is lost and the popup will confidently show the old mode as current. So on every initialize() and on popup open, read -P (pending mode) and -p (pending action) and restore the confirm strip from them. -P returns Unknown and -p returns No action required when nothing is staged.

Consequence: pendingMode should be service-owned and sourced from the daemon, reversing the previous draft's "prefer UI-local" call. UI-local state keeps only the pre-confirm selection, which by design has not touched the daemon yet.

Reading always_reboot

Two options. Prefer FileView on /etc/supergfxd.conf — it is 0644, plain JSON, already an established idiom in this codebase (Notifications.qml, PresetsService.qml), and it reacts to external edits. The D-Bus equivalent is busctl --system call org.supergfxctl.Daemon /org/supergfxctl/Gfx org.supergfxctl.Daemon Config → ubbbbtu = (mode, vfio_enable, vfio_save, always_reboot, no_logind, logout_timeout_s, hotplug_type); use it only as a fallback if the file is unreadable.

9. Implementation phases

Phase A Service skeleton

  • Create SuperGfx.qml: -v probe → -g / -s / -p / -P.
  • Strip ANSI escapes from all output before parsing. Parse -s as bracket-stripped comma-space list.
  • Filter to Integrated / Hybrid / AsusMuxDgpu; sort in that order.
  • FileView on /etc/supergfxd.conf for alwaysReboot.
  • Verify against the real daemon on Zephyrus; verify the unavailable path on Bostrom as-is.

Phase B Idle UI, read-only

  • Graphics RowLayout under profiles, bound to availableModes / currentMode.
  • Match profile-button styling exactly, including first/last radius rules and StyledToolTip.
  • Fix profilesRow's Layout.fillHeight; extend contentHeight per §5.
  • No click handler yet — confirm the row hides cleanly on Bostrom first.

Phase C Predict + confirm

  • Click → predictAction() → pending highlight + confirm strip. No daemon call.
  • Cancel restores selection to currentMode.
  • Confirm → setMode() → compare returned action to prediction → run session command only on match.
  • Restore staged state from -p / -P on init and popup open.

Phase D Hardening & validation

  • Error path: daemon down mid-session, mode rejected, non-zero exit.
  • Poll currentMode on popup open (cheap, catches out-of-band changes).
  • Bostrom: start supergfxd manually for a test window, from SSH, Moonlight closed. Do not enable at boot.
  • Zephyrus: validate the AsusMuxDgpu path — and the way back out of it — last.

11. Risks & open questions

ItemStatus
Does axctl system exit work? Open — verify before relying on it anywhere. Probing axctl system exit --help returned hyprland rejected request: hl.dispatch: expected a dispatcher (e.g. hl.dsp.window.close()), suggesting axctl v0.0.19 emits the deprecated hl.dispatch(exit) form. If PowerMenu's logout is broken on the installed Hyprland, that is a separate bug worth filing — and a reason this feature should not inherit it. Exiting AsusMuxDgpu Open — verify on Zephyrus before shipping the Mux button. supergfxd defines GfxError::AsusGpuMuxModeDiscreet ("Can not switch gfx modes when discreet/G-Sync mode is active"). The action matrix does map AsusMuxDgpu → Hybrid/Integrated to Reboot, so the exit path is intended to work, but the guard's exact trigger was not confirmed from source. Worst case the row goes inert while the MUX is engaged. Confirm the round trip works before the Mux button ships, not after.
Competing control path Four fish functions (gpu-school, gpu-mixed, gpu-game, gpu-status) already switch modes by sed-ing /etc/supergfxd.conf and rebooting, bypassing supergfxctl entirely. They exist because the daemon path was broken. Once this widget ships there are two divergent ways to change mode — and the functions are what generated the eight /etc/supergfxd.conf.bak* files. Bostrom dGPU may not return hotplug_type: "None" + non-ASUS chassis: Integrated removes the dGPU from the PCI bus and the rescan back is not guaranteed. Test Hybrid → Integrated → Hybrid as a round trip, from SSH, before trusting it.
